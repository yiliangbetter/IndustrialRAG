# 澄清门控优化 — 两条测试路线

> 状态：路线 1 实施中；路线 2 已实现（`CLARIFY_CANDIDATE_SKIP_PROBE=1`）

## 路线 1：收紧澄清 probe 预算 + 分阶段计时

**目标**：在保持 v4 rerank 门控（推荐须 `final > CLARIFY_DIRECT_RERANK_MIN`）前提下，缩短澄清循环耗时。

**`.env` 建议**：

```env
CLARIFY_CANDIDATE_MAX_ROUNDS=1
CLARIFY_CANDIDATE_MAX_PROBES=3
```

**批测**：

```powershell
uv run python scripts/bench_clarify_green8.py --source green8 --pick random --seed 42
```

**报告字段**（`generation.gate_timing` / bench 逐题）：

| 字段 | 含义 |
|------|------|
| `original_probe_s` | 原问 1 次 mix+rerank |
| `candidate_gen_rounds[]` | 每轮推荐问 LLM 耗时 |
| `candidate_probes[]` | 每条推荐 probe 耗时、`final_score`、是否过关 |
| `candidate_gen_total_s` / `candidate_probe_total_s` | 汇总 |

---

## 路线 2：推荐问不做 rerank 门控（LLM-only 澄清）

**目标**：原问 probe 后，**仅用**原问检索到的 chunks + LLM 生成 2 条推荐问；**不对推荐问再 probe / 不按 final>7 筛选**；用户点选后走正常全流程 `aquery`。

**与路线 1 差异**：

| | 路线 1 | 路线 2 |
|---|--------|--------|
| 推荐问生成 | LLM + chunks | 同左 |
| 推荐问验收 | 每条 mix probe + `final>7` | **无** |
| 点选后 | bundle 注入（probe 缓存） | 全量 `aquery` 或按需注入 |
| 风险 | 凑不满 k → reject | 推荐可能 rerank 低但 LLM 可答 / 反之 |

**实现**：`.env` 设 `CLARIFY_CANDIDATE_SKIP_PROBE=1`（默认 `0` = 路线 1）。原问 probe 不变；推荐问仅 LLM 生成 **k 条**（不再多请求缓冲条数），跳过 probe；点选后无 bundle 注入，走全量 `aquery`。

```env
CLARIFY_CANDIDATE_SKIP_PROBE=1
```

## gate 耗时不稳定 — 诊断

**现象**（如 `bench_clarify_green8_20260629_214557`）：`original_probe_s` 17s～385s，但 `candidate_gen` 稳定在 ~13–18s；**不是推荐 probe**（路线 2 已为 0）。

**对照** `standalone_rerank_stress`：Qwen 对 ~70 chunk 连续 8 轮 ~6s/轮、**无劣化** → 瓶颈在 **mix 全链路**（向量/KG merge pool 大小、多路 rerank），而非 rerank 模型显存泄漏 alone。

**诊断命令**（只跑 probe，不答题 LLM）：

```powershell
uv run python scripts/bench_probe_timing_green8.py
uv run python scripts/bench_probe_timing_green8.py --repeat-each 2
uv run python scripts/bench_probe_timing_green8.py --gc-between
uv run python scripts/standalone_rerank_stress.py --model Qwen/Qwen3-Reranker-0.6B --rounds 8
```

**优化方向**：路线 2 已省推荐 probe；probe 与 answer 分离批测（`--gate-only`）；关注 merge pool 过大题（#14）；答题后 GPU 争用时可试 `--gc-between` 或 gate-only 批测。
