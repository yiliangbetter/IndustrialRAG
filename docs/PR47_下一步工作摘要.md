### 4.1 核心思路：配图 ↔ 灌库耦合

现状两者**脱耦**：灌库侧 `induce_field_schema`（`raganything/ingest_coalesce.py`）已归纳每篇文档的字段角色（initiator/closer/metadata_keys），但**只在 coalesce 期间临时用、不落库**；落库 chunk 仅带 `file_path` + 极简 metadata。于是查询侧配图只能事后用 hardcode 反推（机型词表 `_KNOWN_MACHINE_NAMES`、字段名/话术正则）——灌库算过、查询又用 hardcode 重猜一遍。

**方向**：把灌库已算出的机型 / 字段 schema **持久化**，查询侧直接读，hardcode 从“查询侧猜”变为“灌库一次算清、查询直接读”，复杂度移到最该待的灌库侧。

**前提：需重灌**。当前 KV 灌于 2026-07-10，已落后于灌库代码（`a023f3f` / `e5a5328` 在 07-28），重灌本就不可避免，正好趁此把元数据落库。

> - 新增 `scripts/iqr_machine.py`：`known_machine_names()` 从 KB chunk 的 `machine` 字段动态归纳词表（file_path 派生兜底，**无需重灌即可工作**，按 KV mtime 缓存）；`resolve_machine_name()` 去空格最长匹配。

**B. 字段 schema 落库——❌ 可行性验证后不做（2026-07）**：原设想将 coalesce 归纳的 `DocFieldSchema` 落库，让查询侧删 `_ANSWER_STRUCTURAL_LABEL_KEYS` / `_MAINT_TOPIC_RE` 等话术正则。

> **验证结论（前提不成立）**：对 5 本目标手册真实 chunk 比对——手册实际字段键（54 个：保养周期/保养内容/保养步骤/操作步骤/…）与 `_ANSWER_STRUCTURAL_LABEL_KEYS`(14) **仅重叠 1 个**（保养周期），与 `_COMPONENT_FIELD_KEYS`(保养部件/润滑部位) **重叠 0 个**；且这些标签**既不在手册数据、也不在任何 prompt 模板**（全仓仅 `iqr_figure_target.py` 自身）。它们是**从 LLM 答案输出观察归纳的「答案呈现标签」**，与源手册 schema 几乎不相交。故 schema 落库替代不了答案标签 hardcode，B 不做。
